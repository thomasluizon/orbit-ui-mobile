screen  The conversation exists so a person can say what they did or what they want and have it happen. It is not a transcript and not a help desk: every answer that touches data comes back as a block with controls in it, because a read only card is a screenshot of the app pasted into a chat. Prose appears only where there is nothing to operate on.

states  empty, preview, preview acting, stale, habits, goals, goals empty, clarification, metrics, breakdown, conflict, batch failed, the five operation outcomes, streaming, busy, recording, transcribing, attachments, offline, at limit, model error, copy, loading. A plan axis sits beside the state, free or Pro, defaulting to free: at limit free and at limit Pro came OFF the state axis in the same edit, because a plan is an account fact that survives a state change, and one at limit state now reads its ceiling from the plan, 5 against 50 (D70 item 1). Reached by using the screen rather than the axis: recording by pressing the microphone, transcribing by pressing stop, the transcript landing in the field as composing, the attachment tray by attaching, a remove per item, the empty state’s suggestions each opening a drawn answer, and the goal rows and chip leaving for Progresso. The logging check, the pagination, the frequency pills, the accept confirmation and the copy control all work.

preview  one batch preview, per item edit, one accept. Three actions, approve edit reject, never a single OK, because a single OK gives the person no way to change one line without discarding the rest. The payload is withheld until approval, so the preview is a preview: nothing in it has been written. It never auto dismisses. Rejecting it collapses the block in place to one line naming what was declined: keeping the block with spent actions would read as broken rather than finished, and removing it would leave a person scrolling back unable to tell a decline from a failure. An irreversible row differs from a reversible one by the frame's own neutral mark, so it is a shape and a word rather than colour alone, and because one row is irreversible the frame states in the action row that the accept asks for a confirmation. Bulk log and bulk skip carry none, since both are reversible. Answered 2026-08-18: a partially failed bulk create keeps the rows it created and the retry covers only the failures. There is no batch undo, so the partially failed frame offers the retry and nothing that promises a rollback.

habits  the same two controls the list has everywhere: the trailing ring logs optimistically and rides in the row's control slot, and the label is the tap target that opens the habit. The chat teaches no new gesture. Pagination pages in place and the header count moves with it, so a reply never drills out into a full list.

clarification  one short question with tappable answers, which the contract requires whenever Astra cannot resolve what was said. It is not politeness: guessing between two habits with the same verb writes the wrong log, and a wrong log is worse than a question.

metrics  one overview answering how the period went, three real figures and a chip through to Progresso. No per habit drill in inside the chat, and no chart: the numbers are rows, which is what the system can draw honestly.

goals  the sixth block (goal-list-card.tsx, rendered by message-bubble.tsx:165-166 off message.goalList; [[orbit:goals]] is D69’s third directive token). One row per goal through the same BlockFrame as the other five: the name, its figure with the deadline where one exists (chat.goalList.percentage, .progress, .deadline), and its ring in the row’s control slot, the done disc at 100 because completion is never the accent. A goal row opens the goal, because the chat opens the goal detail from a card today (chat/page.tsx:214), exactly as a habit row opens the habit (:208), and the chip goes through to Progresso. Its own empty line (chat.goalList.empty) says a goal starts from a habit or from an ask, so the empty block still routes somewhere real.

breakdown  rows plus a frequency control per row, each one the row's own control rather than a single group under the list, so a cadence is changed where it is read. Every row it would change carries the proposed flag, which the frame renders at fg-3 inside a dashed hairline, and it never takes the accent. When the proposal collides with something that already exists the block says so above the actions, with the caution glyph and the name of the thing it collides with.

block rules  loading, resting or acting, never half of two: in acting every row shows the acting glyph and the actions are disabled as one, rather than one row spinning inside a resting block. Text streams and the block arrives whole, so the streaming state shows prose mid-stream with no block yet, and no block animates its own reveal. A stale block says so and offers a refresh instead of acting on state that already moved.

announce  announcements are card scoped: each block body is its own polite live region, so a result is read where it happened, and the feed carries aria-busy for the length of a batch rather than announcing every row into the page.

operation  five typed outcomes, each with its risk class stated as a neutral badge: pending confirmation on a destructive batch, step up where identity has to be reconfirmed, denied where the account cannot do it, unsupported by policy where Astra is not the place, and the terminal succeeded. Failed is the same per item shape as the partially failed batch. Risk is low, destructive or high, stated in the frame's header slot beside the count, and on the destructive batch every row also carries the frame's irreversible mark, so risk is never carried by one badge alone. Step up, answered 2026-08-18: it is a hand off, and the hand off is structural now rather than a drawing choice. StepUp has no children prop and no slot of any kind, and every prop on it is a string, a boolean or a handler, so no caller can nest a credential field into it. A credential field inside a chat is the shape of a phishing screen, and prose lost to that defect twice before the type carried it.

boundaries  managing the subscription, the API keys and the account left the chat and live only in Perfil, so those three arrive as unsupported by policy with one action that opens Perfil. Astra never pitches the paywall and never starts a checkout, which is why the denied outcome states the boundary and stops there, with no upgrade action anywhere on this surface.

limit  the allowance is daily, 5 free and 50 Pro, one at limit state reading its ceiling from the plan axis. Both refusals say the list keeps working and that speaking does not spend a message, and neither carries an upgrade path: Astra never pitches the paywall and never starts a checkout, so this screen passes the plan axis and still has no route to Orbit Pro. That is not an omission: the axis exists to draw the two ceilings honestly, and the no-upsell boundary is the decision. The refusal arrives on the stream as an inline error event, so it renders in the thread where the answer would have been. Nothing says when the allowance returns, because no endpoint returns that moment.

busy  the concurrent limit is exactly one, so a second message while one is in flight is refused rather than queued. The composer's own busy state carries it: the send control goes neutral and inactive rather than accent, which is what separates refused from accepted, and the refusal sits inline under the bar. There is no queue and no draft buffer, because a queued message would act on state the person can no longer see.
