screen  Two surfaces for finding something, in one document because they are the same surface at two entry points: search, which had a control in the sidebar and no result anywhere, and the command palette, which is that field plus the actions and destinations. At 412 they are the same sheet reached from the same field.

states  searching, no results, one result, many results, palette resting, palette typing, palette loading, the log page, the skip page, palette no match. Hover, focus-visible and press are live. Reached by using the screen rather than the axis: the second page by choosing log a habit or skip a habit, the way back out of it by its own back control or Escape, and the active item by the arrows. No plan axis: this screen has no gate, and a screen with no gate does not grow a dead switch.

match field  the API already returns which field matched, and the app has never rendered it. Every result states it: the title, the description, a tag, or a child habit. A row whose title does not contain the query would otherwise look like a mistake, and a person cannot tell a tag hit from a description hit by looking at the name. The fragment is quoted beside the field name only where the API returns one: SearchMatchField(string Field, string? Value) passes a null Value for title (HabitScheduleFilters.cs:255) and description (:257), the tag name for tag (:260), and the child habit's title for child (:284). So a title or description hit states the field and quotes nothing, which still answers why the row came back, and the line keeps one shape on all four rows.

results  one vocabulary for every result: the emoji well, the habit name, then the match line in mono. A child habit match names the parent, because that is the thing the person will navigate to. Rows lead to the habit detail, which is the only place a habit can be acted on.

searching  the field keeps what was typed and the list below it holds its own shape, so nothing jumps when the results land. It is three dots on a row rather than a spinner over the screen, because the query is fast and the field must stay usable while it runs.

no results  states the query back, says nothing matched, and offers the one action that makes sense from a search that failed: create a habit with that name. It parks no mark and no illustration, because this is a transient state inside a field, not a destination.

palette  at the wide width it is a centred overlay opened from the sidebar control or Ctrl K; at 412 there is no keyboard shortcut, so it is the same list reached from the search field. FOUR groups in the app’s order (command-menu.tsx): the habits (:122), holding their shape with the skeleton while they load (CommandHabitSkeleton, :118); create (:194-205), which here is create habit alone, because D69 item 9 removed the create goal entry, so a goal is made from a habit or by asking, and that half is a decision rather than a loss; actions (:209-221), log a habit and skip a habit; and the destinations (:224-226). Choosing log a habit or skip a habit does not act: CommandPage (:15) opens a SECOND page listing the habits to act on, with a back control (:155) and the page’s own word in the field’s chrome (:113), and choosing a habit there is what logs or skips it (:140-141). The single log everything action this document used to draw did something the palette never does, and it is gone. When nothing matches at all, the palette says so with its own line (command.empty, :188), which is not the same thing as a group being absent.

keyboard  the palette is a listbox: one item is active at a time, the active item takes the selected tint and ring rather than a fill, arrows move the active item without moving focus out of the field, Enter chooses it, and Escape backs out of a page before it closes the palette. The foot carries the hint row the app draws (CommandKeyHint, :247), keycap and word pairs starting with the up and down arrows, not one escape line.

accent  current position on the active palette item and the focused field ring. One filled action in the no results state, which is the create; none anywhere else, because a list of results is a list of actions and marking one of them would be a guess.

contrast  the match line sits at fg-3 on the canvas and the quoted fragment at fg-2, so the quote reads above its label. No status colour appears; nothing here is an error, including no results.

mock  the result count and every quoted fragment carry data-mock, along with the query itself.

tests  1 every result states which field matched. 2 no result leads anywhere except a habit or one of the four destinations. 3 the field stays usable while a query is running.

gaps  the mirrored bundle was checked before use, as every round since it first went stale: it already carried Input’s trailing slot, so nothing was re-synced. The old gap 1 said forms has no search field, so the field was a composed input; Input’s trailing slot closed that, and both the search field and the palette field are now the same Input the move sheet on Hoje uses, with the glyph in the slot. Still composed around the system: 1 there is no result row, so it is composed from a well, an emoji and a mono match line. 2 there is no palette or listbox in overlay, so the palette is composed from an elevated panel; Menu is an overflow menu and the wrong semantics for a filterable list. 3 the page chip in the field’s chrome and the keycap pairs are composed, since neither has a component.

open  whether a tag hit should offer to filter by that tag rather than open the one habit, which no surface currently supports. Whether the palette should search logs and notes as well as habits, which the endpoint does not cover.
