screen  Offline is not one screen, so it is not drawn as one. There is no offline page anywhere in this document. It is drawn as the two behaviours the product actually has: on mobile the change is queued and the row moves anyway, and on the web a small number of surfaces refuse in place and say so.

states  queued, syncing, failed retrying, synced, dropped. Switch the width control to see the other half: 412 carries the queue and its toasts, wide carries the refusals. Tapping a ring at 412 queues another change, so the mechanism can be exercised rather than only read; every other host control is scenery and wired to nothing, said here once. NO plan axis: nothing here is gated, because being offline is not a plan boundary, so the absent switch is a decision.

mobile  the row mutates optimistically and carries no pending mark of its own. That is deliberate: a per row clock or dimming would tell a person their log did not count, when it did, and it would put a spinner on the one gesture in the product that is guaranteed never to fail. The whole mechanism lives in three global toasts instead, so there is one place to look and the list stays exactly as it reads when online.

queue  the queue holds CHANGES, not logs: packages/shared/src/types/sync.ts:3-13 lists about fifty mutation types, covering creating, updating, deleting and restoring a habit, a goal or a tag; logging and skipping; reordering; checklists; sub habits; every bulk action; notifications including mark all read and delete all; every profile setting from the name to the theme to the time zone; completing onboarding; and creating or deleting an API key. So the toasts count alterações, never registros. The queue also orders and deduplicates itself: sync.ts:39-57 gives every change a dedupeKey, a dependsOn list, a clientEntityId and a targetEntityId, and offline-mutations.ts replaces entity references once a real id comes back, so a habit created offline and then logged offline lands in the right order with the right id, and the same change made twice is not sent twice. That is the reason the drawing can promise the queue drains itself, and why the neutral toasts carry no action.

toasts  four now, and the first three are the same object in three of its states. Queued says the changes are held on the device and counts what is waiting; syncing says they are going up now, with the three dot mark the Toast draws itself; synced says everything landed, and it is the only one that leaves on its own, through onDone. Between syncing and dropped sits the status the store actually has: sync.ts:37 declares pending, syncing and failed, and offline-mutations.ts:540 with :545-561 writes failed with the error and a retry count while the change stays IN the queue. The failed retrying toast is neutral, names no loss because there is none, carries no action because the retry is the queue’s own, and must never read like dropped. The composer’s offline half took an onRetry this round, valid only in that state for a message that failed to send; it is deliberately not passed here, because nothing has been sent on this screen and a retry with nothing to retry is a dead control.

dropped  this is the one that loses data. The client bounds the queue itself: maxRetries is 3 (offline-mutations.ts:118), and :342-346 drops a change on the third failure, or immediately when the error is one retrying cannot fix, which is exactly what makes a dropped state honest to draw. The toast names which change was lost, states that the rest of the queue did land, and offers the one action that fixes it: do it again, from here, in one tap. It carries the error hue because something was genuinely lost, and it never leaves on its own. The client also HAS the reason: offline-mutations.ts:48-52 hands the listener the id, the type and lastError, so support can be given a cause even though the raw error stays out of the line.

web  the web has no queue, and that is verified rather than assumed: apps/web/hooks/use-offline.ts is 25 lines and returns one boolean. So a small number of surfaces refuse and say so in place, next to the control that will not work: the composer, creation, and calendar sync. Everything else keeps working, because reading is served from what was already loaded. One refusal sentence is WEB ONLY and must not be carried to mobile: creating needs a connection on the web because the habit is made on the server there, but on mobile createHabit is a queued type with a client side id that is swapped for the real one when it lands, so a mobile creation works offline like any other change.

accent  the queued and syncing toasts carry no action and no accent. The dropped toast's redo is the one filled action in that state, because it is the next action in the strictest sense. Rings that were logged while offline are neutral fg-1, exactly as they are online.

contrast  status-bad appears only on the dropped toast, paired with a glyph and a sentence, never as colour alone. The other three toasts are neutral wells at fg-2.

mock  the queue count, the habit times, the name of the dropped change and the allowance number inside the composer’s limit reason all carry data-mock.

tests  1 no row carries a pending mark. 2 a dropped change names what was lost and offers to redo it, and a failed change never reads as loss. 3 the web never claims to have queued anything.

gaps  1 closed: Toast exists in overlay, discriminated on kind, and the four states here are its four kinds: queued is neutral with the wifi-off glyph, syncing is working with the component's own three dot mark, synced is done and unmounts through onDone, and dropped is lost, which the type cannot construct without its detail line and its way back. All four ride the shells' notice slot, with the composer restored beside them. 2 there is no inline refusal component, so the web refusals are composed from a well, a glyph and two lines.

open  whether the synced toast should appear at all when the queue was one item, since the person may never have known it was queued.
