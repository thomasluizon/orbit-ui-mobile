screen  The step up challenge guards the two operations that can outlive a session, and nothing draws it today. It states which operation is being confirmed at the top, in the eyebrow, because a code screen that does not name what it authorises is indistinguishable from a phishing page.

operations  two, not three. Delete account ships this challenge today: AuthController.cs:295-325, request-deletion then confirm-deletion. API keys is Thomas's decision, tracked as ticket #342 on the api: today ApiKeysController.cs mints a key behind ordinary session auth with no re-check, and a key outlives the session and grants the whole MCP surface, so this screen is ahead of the backend and #342 is what closes that gap. Billing is not a step up operation and is not in the enum: it hands off to the Stripe customer portal, which authenticates the person itself, so a code before opening it is friction that buys no security.

states  challenge, typing, checking, wrong code, resend ready, expired, exhausted, deactivated, deactivated pro. Hover, focus-visible and press are live. NO plan axis: the screen has no gate, and the Pro variant of the deactivation date is a date, not a gate, so the absent switch is a decision rather than an oversight.

hand off  this screen is the hand off. The conversation sends a person here rather than asking for a code where they stand, and it is reached from Perfil only. A credential field inside a chat has the shape of a phishing screen, so the note at the end says plainly that Orbit never asks for a code in a conversation.

before  the step before this one belongs to Perfil: the app asks for a plain confirmation first, with its own warning card, and only then sends the code (delete-account-modal.tsx:128-137 and :50-61), and the code step can walk back to it (:150). So the operation named in the eyebrow was already confirmed once, this screen is the SECOND gate and not the first, and the way back from here is the cancel link, which routes to Perfil. The app runs the whole thing as a modal inside Perfil; drawing it as a full screen that takes over is this redesign’s own position, and it stays.

success  the code being right is the most consequential thing on the screen, and it does NOT delete: ConfirmAccountDeletionCommand.cs:41-51 voids the challenge and deactivates the account with a date SEVEN DAYS out, or seven days after the plan expires for an account with Pro (:44-46), capped at 30 days (AppConstants.cs:44), and the endpoint returns that date (AuthController.cs:320). The deactivated state carries the date in the person’s own date format with data-mock, says the account comes back whole if they sign in before then, which is true (VerifyCodeCommand.cs:104-109), and its one action signs them out (delete-account-modal.tsx:163), landing on Entrar. The Pro variant states the plan’s own end date on its own line, because a person who paid needs to know the plan is not being thrown away.

constraints  four real numbers, each drawn rather than described, and each from the account deletion flow rather than the agent platform: the 5 minute, 5 attempt step up in AgentPlatformSettings.cs:9-11 governs a pending agent operation, which this screen is not. The challenge lasts 10 minutes, RequestAccountDeletionCommand.cs:44, so the hint states the window and the expiry is its own state. Resend has a 60 second cooldown, RequestAccountDeletionCommand.cs:33, and the challenge ARRIVES with that cooldown already running, because this screen is opened by the send itself (RequestAccountDeletionCommand.cs:28-34 refuses a second code within 60 seconds): the plain challenge state shows the mono countdown, and only resend ready holds the control. There are 3 attempts (AppConstants.cs:42, checked at ConfirmAccountDeletionCommand.cs:27), and they are neither per challenge nor per hour: the counter is keyed delete-attempts:{email} (ConfirmAccountDeletionCommand.cs:68) over a rolling 15 minute window (:64, AppConstants.cs:43), PER EMAIL ADDRESS, so a new challenge does not restore them.

failures  three, and they differ in what they offer. A wrong code leaves the field usable and states the attempts remaining over their 15 minute window, because retyping is the fix and a count without a window is half a fact. An expired challenge disables the field and offers a new challenge, because retyping a dead code cannot work. Exhausted attempts void the challenge entirely: the notice states the 15 minute lock the way Entrar’s lock states its own, says plainly that a new code does not restore the attempts, and offers NO action that would be refused, because starting again from Perfil inside those fifteen minutes hits the same per-email wall. The quiet route back to Perfil is the way out of the screen, never presented as the way to try again.

attempts  the count is stated as attempts remaining rather than attempts used, because the number a person needs is how much room is left. It is never phrased as a warning and never named as a mistake.

accent  one filled action per state where a way forward exists: confirm while the challenge is live, a new challenge when it expired, sign out on the deactivated states. Exhausted carries NO filled action at all, because every forward action there would be refused for fifteen minutes, and the route back to Perfil is a quiet ghost. Current position is the focused field ring and the active digit cell. The resend is a quiet ghost, so the primary and the secondary path are never confusable.

shell  no shell: a challenge takes over, so there is no tab bar to wander off through and no composer, and cancelling is an explicit link rather than an escape. At the wide width it is the same column centred in a panel.

contrast  white on primary 4.57:1 rest, 5.11:1 hover, 6.09:1 pressed. status-bad carries the wrong code, ringing every cell because the code is wrong as a whole, paired with a sentence stating the attempts left. The exhausted notice is neutral, because a spent attempt count is a boundary rather than a fault.

mock  the cooldown, the attempts remaining and their 15 minute window, the 10 minute window, the address the code went to, the lock countdown, and the deactivation dates on both success variants all carry data-mock.

tests  1 the screen names the operation it authorises. 2 each failure offers only an action that can succeed, and the exhausted state offers none that would be refused. 3 no code is ever requested outside this screen. 4 the success state promises only what the server returns: the date, and the way back before it.

gaps  the OtpInput gap is closed by wave 3: one real input spans the cells, so typing, backspace, autofill and pasting a whole code are the component's, and the wrong code message is its error state. Still composed: 1 attempts and cooldown are mono lines, there being no counter affordance in the system. 2 CapacityNotice carries the exhausted state, which is a rate limit rather than a plan ceiling.

open  whether cancelling should say the operation was abandoned, which no endpoint confirms. Whether the deactivated state should offer anything besides signing out, which the app does not.
