screen  Four surfaces a person meets when something is wrong or missing: the update gate, a page that does not exist, a generic failure, and a refusal for rate limiting. Each states the fix. None of them apologises, and none of them says oops, sorry or something went wrong.

states  update, update soft, not found, failure, throttle. The update state renders differently at each width, which is the point: switch the width control to see both halves of the divergence, and the soft update is a 412 shape, because the store check it comes from does not exist in a browser. NO plan axis: none of the five is a plan boundary, because a rate limit is not a ceiling a plan lifts, so the absent switch is a decision.

update  the gate has TWO independent sources. The server gate: MinimumVersionMiddleware.cs:26 reads the X-App-Version header, :41 compares it against the configured floor, and :53-63 answers 426 with minVersion in the body. Web picks that up at api-fetch.ts:88-91 and draws a DISMISSIBLE banner with a reload (update-available-banner.tsx:24,53), because the web app is brought up to date in place by loading it again, and a blocker would take a working session away for a fix that takes a second. Mobile picks it up at api-client.ts:222 and draws a NON DISMISSIBLE full screen blocker with a store action (upgrade-required-screen.tsx:23), because a build that is too old cannot talk to the API at all. That gate is FAIL SAFE and currently OPEN: a missing or unparseable header is always allowed and the floor defaults to 0.0.0 (MinimumVersionMiddleware.cs:17-20 and :38-39), so nobody is blocked today. The STORE check never touches the API: use-version-check.ts:41 asks Google Play directly and :49 asks the iTunes lookup, and two more mobile shapes come from it. The SOFT update, an update that exists and is not forced (version-update-drawer.tsx:77), is a dismissible drawer with a store action, drawn here on Sheet because dismissibility is the point. The FORCED store update, when Play reports an update priority of 4 or higher (use-version-check.ts:88), starts Play’s own immediate update flow (version-update-drawer.tsx:86-90), which is Play’s screen and not Orbit’s, so no drawing of it belongs here. Three mobile shapes, one web shape, all traced.

not found  says the page does not exist, names the likeliest cause in plain words, and offers the one destination that always exists, routed to Hoje. One deliberate divergence from the shipping screen: apps/web/app/not-found.tsx:19 draws a satellite glyph at 104, but the system holds no satellite and DESIGN.md allows exactly two identity carriers, the orbital mark and the Astra glyph, so the mark is drawn instead and this sentence is what keeps the drawing from being read as a claim about the shipping screen.

failure  the boundary this state draws is apps/web/app/global-error.tsx. It states that the request did not finish and that nothing was changed, which is the fact a person actually needs, then offers the retry, which goes busy while it runs. The reference code is real, not invented: every failing response carries x-orbit-request-id, set for the version gate at MinimumVersionMiddleware.cs:55 and for a rate limit at DistributedRateLimitAttribute.cs:79, and the client reads it (login-form-helpers.ts:89). It sits in mono at fg-4 because a person contacting support needs it, but it is never the headline.

throttle  the server refuses with more than a countdown: DistributedRateLimitAttribute.cs:73-97 sends a Retry-After header in seconds AND a body carrying retryAfterUtc, limit, count and requestId. The screen CHOOSES to show only the countdown, whose producer is retryAfterUtc: the limit and the current count explain nothing a person can act on, and the moment to try again is the whole fix. It does not guess which action tripped the limit, because the response does not say that, and it does not blame the person. The retry control is present and disabled while the countdown runs, so the way back is visible without being pressable. Backgrounding cannot desynchronise the countdown, because retryAfterUtc is an absolute moment and the remaining time is recomputed from it at any instant.

voice  every one of the four names the circumstance, states the fix, and stops. No exclamation mark, no apology, no reassurance the product cannot back up.

accent  one filled action per state, always the way forward: the store button, the reload, the destination, the retry. The throttle state has none, because its only action is disabled, and a disabled accent would be an invitation the screen cannot honour.

contrast  white on primary 4.57:1 rest, 5.11:1 hover, 6.09:1 pressed. No status colour appears on any of the four: an old build, a missing page, a failed request and a rate limit are all boundaries, and status-bad is reserved for a habit a person is avoiding.

mock  the countdown, both version numbers in the mobile blocker, the version in the web banner and the reference code all carry data-mock, and no other number renders on any of the five surfaces.

tests  1 each surface states a fix a person can act on. 2 the mobile gate cannot be dismissed and the web banner can. 3 the throttle states no reason.

gaps  1 there is no banner component, so the web gate is composed and rides the shell's header slot. 2 Sheet is dismissible by design, so the mobile blocker is composed as a full bleed layer in the sheets slot with no close affordance and no scrim tap. 3 ErrorState centres a message and one action, which suits an inline failure but not a full screen, so these four are composed.

open  whether the web banner should become a blocker after some number of dismissals, which no client currently tracks.
