screen  Entrar gets a person in and nothing else. It is not a place to explain the product: the mark, one line, the field, and the two ways in. No feature list, no screenshots, no plan, no testimonial, and no second heading restating the first. Two exceptions, both earned: the legal line, because this is the only place a person agrees to anything, and the habit count on the arrival from onboarding, because that something is the person’s own habit.

identity  the sign in IS the sign up: SendCodeCommand.cs:22-63 never looks a person up, and VerifyCodeCommand.cs:35 creates the account on the first correct code. That is why no account not found state exists anywhere on this screen, and why no attacker can learn from it whether an address has an account. The screen is shaped by that fact.

referral  the landing of the growth loop: use-login-flow.ts:60 reads the referral_code cookie a shared Wrapped link set, and login-sections.tsx:93-133 draws the banner above everything, a mono eyebrow between two hairlines, a polite live region. The words promise nothing to a person who already has an account, because the referral is applied only when the account is NEW (VerifyCodeCommand.cs:100-101): it says the invitation applies when a new account is created, and no more.

arrivals  two more ways in than the plain visit. From onboarding (the signed out path’s other end): the heading becomes the save your plan title (login-sections.tsx:32-40), the subtitle swaps and a line counts the habits waiting on the device, with singular and plural forms (:70-81), and the button’s word changes with them (page.tsx:81-83); the count is drawn with data-mock. From a link: when the address carries an email and a valid code, the screen opens ALREADY on the code step with the six digits filled and the verify ready to press (use-login-flow.ts:78-86).

states  email, email invalid, referred, from onboarding, sending, send failed, code, code typing, from link, code wrong, code expired, locked out, resend ready, verifying, google, google failed, account back, offline. Hover, focus-visible and press are live. Two steps only, the step inferred from what the person has done. NO plan axis: there is no gate and no plan before a person is in, so the absent switch is a decision, not an oversight.

typing  the sixth digit submits on its own: use-login-code-entry.ts:41-49 fires the verify as soon as six digits are present, deduped so one code submits once. The button (code-step.tsx:87-96) stays, so both exist, and in this drawing the verifying state is reachable from the sixth digit as well as from the action. The confirmation that a code went out is drawn too: use-login-flow.ts:117 sets it after the send and :174 again after a resend, a polite live region (login-sections.tsx:183-226), so the move from the email step is never silent. And a returning deleted account is told its account is back: VerifyCodeCommand.cs:104-109 cancels the deactivation when a deactivated account signs in, and login-form-helpers.ts:110-112 shows that as the success line, drawn here as its own state with one action into Hoje.

failures  the code has three failures and they are three different screens, because they need different copy and different actions. A wrong code says it does not match and leaves the field usable, since retyping is the fix. An expired code says the code lasts 5 minutes and offers a resend, not a retype, because retyping a dead code cannot work. A lock after 3 attempts says how long the wait is; it offers no verify and no resend, since those would fail for 15 minutes, but the change of address STAYS, because the lock is PER EMAIL ADDRESS: VerifyCodeCommand.cs:90 keys the counter as verify-attempts:{email} and nothing else, with :87 giving it the 15 minute window, so another address works right away. The email step fails too: auth-login.ts:112 maps 429 to a rate limited message, :114-118 maps every 5xx to a server error, and :123 maps a thrown TypeError to a network error, and all three are ONE send failed shape here, the message beside the action and the typed address kept, because to a person they are the same thing: it did not go, try again. Google can fail as well (use-login-flow.ts:207-213): the failure is a line under the button with the button back at rest, never a separate screen. One defect stays in the code rather than in the drawing: use-login-flow.ts:96-99 sets the inline message AND raises a toast for the same failure; the drawing keeps only the inline message, beside the field it belongs to, and the duplicate toast should not be restored. Every number is the sign in flow’s own, traced 2026-08-20 and re-traced today: the code lasts 5 minutes (SendCodeCommand.cs:56), the resend cooldown is 60 seconds (SendCodeCommand.cs:45), there are 3 attempts (AppConstants.cs:42, checked at VerifyCodeCommand.cs:60), the lock lasts 15 minutes (AppConstants.cs:43, written at VerifyCodeCommand.cs:87), and the code is 6 digits (SendCodeCommand.cs:49).

resend  two states, drawn as two. While the window is closed it is a mono countdown and no control, so there is no button to press that would be refused. When it opens it becomes a quiet ghost action. The countdown is a fixture rather than a live timer, since a canvas that runs a clock forever is a worse review artifact than one that states the moment.

loading  neither step blanks. Sending keeps the email step on screen with the action in its loading state; verifying keeps the six digits visible with the action loading and the field disabled. There is no spinner over an empty screen anywhere in the flow, and no full page loading state exists to draw.

errors  every error sits next to the field it belongs to, in both locales, and states the fix: the email error carries the shape of a complete address rather than the word invalid. No bare code, no status number, no shame. The email error uses the field component's own message treatment, and the code error is the six digit field's own error state, ringing every cell because the code is wrong as a whole rather than one digit being wrong.

offline  a real state on this screen today, so it is drawn on both steps: a neutral notice naming the circumstance, the primary disabled with its reason beside it, and the Google path disabled for the same reason. It is a boundary rather than an error, so no status colour appears.

google  one ghost action under a divider, equal in width to the primary and lower in weight, because most people will use the email path and the accent belongs to it. No Google logo is drawn: the system holds no third party brand asset and inventing one is worse than the word.

legal  one sentence under the Google action (email-step.tsx:91-110), with a link to the terms and a link to the privacy policy. It is not an explanation of the product, and it is the only place a person agrees to anything. Neither document is drawn in this project, so both links land on Sobre.

shell  neither shell is used here, deliberately, and nav false does not change that: this screen has no tab bar, no sidebar, no composer AND no pinned bottom slot, because its actions sit in the flow of the form rather than pinned to the shell’s edge. A single column at 412 and the same column centred in a panel at the wide width.

spacing  4 8 12 16 24 32, gap only. The six digit cells are the component's own 44 by 56, the buttons are 50 tall and full width, and the panel padding at the wide width is 32.

radius  12 on the field, the digits and the wells, 20 on the notice, 28 on the wide panel, 999 on the buttons.

accent  one filled action per step, and it is the step's own forward action, at both widths: with no shell there is no sidebar create button to compete with, so the accent does not step down the way it does on a screen inside the shell. Current position is the focused field ring and the active digit cell. Nothing here marks completion, and the Google path, the resend and the change of email are all quiet.

contrast  white on primary 4.57:1 rest, 5.11:1 hover, 6.09:1 pressed. status-bad carries both error messages and is paired with a dot and a sentence, never colour alone. fg-3 on the canvas is 6.18:1, and the mono hints sit on the canvas rather than on a raised surface.

mock  every number carries data-mock on the element that renders it: the address in the sent line, the resend and lock countdowns, the 5 minutes in the expiry copy, the 3 attempts and the 15 minutes in the lock copy, and the habit count on the arrival from onboarding. The prefilled six digits are the field’s value, not a rendered number.

tests  1 nothing on the screen explains the product, except the legal line and the person’s own habit count. 2 every failure offers only actions that can succeed, including the change of address while locked. 3 no state blanks the screen or hides what was typed. 4 no state reveals whether an address has an account.

gaps  1 closed by wave 3: OtpInput owns the typing, one real input spanning the cells, so backspace, autofill and pasting a whole code are the component's; the wrong and expired messages ride its error state, ringing every cell because the code is wrong as a whole, and the 5 minute line is its hint. The overlay input and the composed error are deleted. 2 the system has no divider, so the or rule is composed from two hairlines. 3 there is no field level countdown or a resend row, so both are composed from mono text. 4 CapacityNotice is the closest neutral boundary and it carries the lock, which is a rate limit rather than a plan ceiling.

open  whether a person returning to a still valid code should see the digits they already typed, which no endpoint reports. Whether the referred banner should persist onto the code step or only sit on the first screen, which login-sections draws but the flow does not state.
