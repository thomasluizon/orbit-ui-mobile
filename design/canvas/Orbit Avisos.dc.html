screen  Avisos answers what did I miss. It is a list of things that happened while the person was away, and every row leads somewhere: the payload carries a title, a body, a link, an optional habit, a read flag and a timestamp, and the row renders all six of those and nothing invented.

states  unread, all read, one item, full list, detail, delete queued, clear all, empty, loading. Hover, focus-visible and press are live. Reached by using the screen rather than the axis: the sheet by tapping a row, the queued delete from a row’s own control or the sheet’s, the undo from the toast, the row coming back when it is taken, and the cleared list from the clear all confirmation. No plan axis: this screen has no gate, and a screen with no gate does not grow a dead switch.

bell  one control, two placements: the mobile shell header and the web sidebar. The count is a neutral pill, fg-1 with canvas text, because an unread count is not a next action, not a current position and not progress toward anything, so none of the accent's four roles covers it. At zero the pill is absent rather than showing a nought, since a nought is a number a person does not need. The count is capped in copy at 9 and over, because the exact figure past that changes nothing a person would do.

read  read and unread differ by more than colour, in three ways at once: an unread row carries a filled dot in a reserved column, its title is a weight step up, and it sits on the card surface while a read row sits flat on the canvas. The dot column is reserved on every row, so nothing shifts when a row is read, and the list never reorders under the person's thumb. Mark all read is drawn in the header as a quiet ghost action, absent at zero unread rather than disabled, the same rule the sign in screen's resend follows: never offer a control that would do nothing. The endpoint and the control both ship today, so the earlier claim here that no endpoint exposes it was wrong: NotificationController.cs:44 is [HttpPut("read-all")], handled by MarkAllNotificationsReadCommand, the bell renders the control at apps/web/components/navigation/notification-bell.tsx:278-282 and apps/mobile/components/navigation/notification-bell.tsx:66, 278, and apps/mobile/lib/offline-queue.ts:183 queues it while offline. No decision removed it, and a capability the app has today is never dropped without one.

acts  a row opens the notification’s own sheet (notification-detail-modal.tsx): the mono timestamp eyebrow with the target beside it, the body in full rather than truncated forever, and the three shipping actions, view (:54-55) as the primary leading to the row’s stated target, mark as read (:59-60), absent once the row is read, and delete (:63-64), destructive and last. A row can also be deleted where it sits: each row carries a real 44px delete, a SIBLING of the row body in ListRow’s action treatment, never nested inside it, its glyph in status-bad paired with the word in its accessible name. The delete is QUEUED, not immediate (notification-bell.tsx:186-192 through pending-notification-deletes.ts): the row leaves at once, a neutral Toast in the shell’s notice slot carries notifications.deleteQueued with notifications.deleteUndo as its action, taking the undo brings the row back, and the toast leaves when the queue commits or the undo lands, never on its own timer, which is the component’s rule. Clear all (useDeleteAllNotifications, the showDeleteAllConfirm gate at notification-bell.tsx:159,165) sits beside mark all read, absent when the list is empty rather than disabled, and it asks first, names how many go, and says there is no way back, because there is not one: the undoable delete says it can be undone, and the one that cannot says that instead.

links  every link points at one of the four destinations or at a habit, and the row states its target in mono so the destination is visible before the tap. The streak notification goes to Progresso, which is where the streak and its repair live. This is drawn as fixed: the shipping payload still writes links to routes the four destination shell removed, so an existing notification can land nowhere, and ticket #334 files the API cleanup.

empty  the mark at 96, one line, and no action, because there is nothing for a person to do about an empty inbox and an action here would be an invitation to somewhere they were not going. It parks no figure and no upgrade call.

loading  the list's own shape, three lines per row, aria-busy, no spinner. The bell keeps its count while the list loads, since the count arrives with the unread total rather than with the list.

shell  this is a pushed screen rather than a destination, so it carries the tab bar but no composer. The header is two lines, because the two list actions, the bell and the title cannot share one 412 row in Portuguese, the longer locale: back, the title and the bell on the first, mark all read and clear all under them, each keeping its visible word. The composer note stands: the composer belongs to the four destinations, and Astra has nothing to add to a list of things that already happened. At the wide width the bell rides the shell's header slot, because the sidebar has no bell slot yet, which is the one component change this screen needs.
